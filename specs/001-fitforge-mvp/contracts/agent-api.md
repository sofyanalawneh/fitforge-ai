# Contract: Agent REST API (backend ↔ Fetch.ai agents)

Internal contract only — never called directly by the frontend (constitution Principle IV,
FR-014). Both agents run inside a single `uagents` `Bureau` process and are exposed via
`@agent.on_rest_post`. A `Bureau` serves all of its member agents from **one shared HTTP
server/port** rather than giving each agent its own port, so the workout and meal agents are
told apart by REST **path**, not port: both are reachable at `http://<bureau-host>:<BUREAU_PORT>`,
with `/workout/generate` and `/meal/generate` respectively (see research.md decision #1).

## `POST /workout/generate` (workout agent)

- **Request**: `{ requestId: string, profile: { fitnessGoal, activityLevel, workoutExperience } }`
- **Response (200)**: `{ requestId: string, content: WorkoutPlanContent }`
- **Response (error)**: non-200 or a timeout — the backend maps this to `502
  agent_unavailable` for the frontend (FR-015)

### `WorkoutPlanContent` shape

```text
{
  summary: string,               # short description of the plan's approach
  weeklySchedule: [               # one entry per training day
    {
      day: string,                # e.g. "Monday"
      focus: string,               # e.g. "Upper Body"
      exercises: [
        { name: string, sets: number, reps: string, notes?: string }
      ]
    }
  ]
}
```

## `POST /meal/generate` (meal agent)

- **Request**: `{ requestId: string, profile: { fitnessGoal, dietaryPreferences } }`
- **Response (200)**: `{ requestId: string, content: MealPlanContent }`
- **Response (error)**: non-200 or a timeout — mapped to `502 agent_unavailable` (FR-015)

### `MealPlanContent` shape

```text
{
  summary: string,                # short description of the plan's approach
  dailyMeals: [                    # one entry per meal slot
    {
      meal: string,                 # e.g. "Breakfast", "Lunch", "Dinner", "Snack"
      description: string,
      notes?: string                # e.g. dietary-preference call-outs
    }
  ]
}
```

## Cross-cutting

- Every request carries `requestId`, generated by the backend, echoed back by the agent and
  included in both sides' structured logs (constitution Principle II).
- Agents receive only the profile fields relevant to their plan type — not the full
  `FitnessProfile` — keeping the boundary minimal.
